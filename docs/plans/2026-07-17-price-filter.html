Filtr cenově dostupného piva návrh

2026-07-17 · backlog #8 (audit feedbacku 2026-07-13) · monorepo na-pivo (Expo + Django)

Co: hospody půjdou filtrovat podle ceny velkého piva, s histogramem rozložení cen v okolí ve stylu Airbnb/Booking a posuvníkem „do X Kč“. Cena bude mít definovaný původ, stáří a expiraci — UI nikdy nepředstírá přesnost.

Jak: backend dostane nový per-pub cenový index (PubPriceIndex) plněný z už existujících tří cenových toků (Zmapuj hospodu, počítadlo, externí menu). /v1/pubs/near cenu aditivně přibalí ke každé hospodě a histogram i filtr se počítají na klientovi z načtených hospod — žádný nový endpoint, funguje to i offline nad cache.

Cíle

  • Definovaný kontrakt: odkud cena je, jak se aktualizuje, kdy expiruje
  • Skutečné filtrování podle ceny (kompas + mapa)
  • Histogram cen v okolí + posuvník ve stylu Airbnb
  • Viditelné stáří údaje („před 3 týdny“, „≈ starší údaj“)
  • API zpětně kompatibilní — vše aditivně

Ne-cíle

  • Žádné nové scrapování cen — jen existující zdroje
  • Žádná historie/graf vývoje ceny hospody (→ Wrapped-styl později)
  • Žádné hlasování o ceně (last-write model stačí)
  • Žádný cenový leaderboard („nejlevnější hospody města“)
  • Přesná normalizace přes objemy ≠ 0,5 l (viz kontrakt)

Co už existuje (zjištění z kódu)

Backlog říká, že cena je „jen datum/placeholder“ — to už neplatí. Ceny reálně tečou třemi kanály; chybí jen referenční cena hospody, čerstvost per údaj a filtr:

Cenový kontrakt

Jedna věta, kterou musí umět říct UI: „Velké pivo tu stojí ~45 Kč, údaj je 3 týdny starý a přišel od lidí z appky.“

  • Referenční cena hospody = nejlevnější pivo z aktuálního menu s objemem ≥ 400 ml (objem null se počítá jako 0,5 l — český default). Malá piva a nápoje mimo pivo se ignorují.
  • Priorita zdrojů: community menu (potvrzené uživatelem) > pozorování z počítadla > externí menu. Novější pozorování z vyšší priority přepisuje.
  • Čerstvost: ≤ 6 měsíců = plná důvěra; 6–12 měsíců = zobrazí se se „≈“ a věkem, filtr ji stále používá; > 12 měsíců = expirovaná — server ji vůbec nepřibalí, hospoda je ve filtru „bez známé ceny“.
  • Aktualizace: každý ze tří write-paths (menu submit, drink merge, externí import) upsertne PubPriceIndex; smazání/vyčištění menu index deaktivuje.
  • Nejistota v UI: vždy relativní věk („před 3 týdny“), nikdy jen holé číslo. Žádné „45,00 Kč“ — celé koruny.
Proč min ceny, a ne medián?

Menu má max 12 řádků a typicky 1–4 oceněné položky; medián by kolísal podle toho, jestli někdo připsal speciál za 95 Kč. „Za kolik je tu nejlevnější velké pivo“ je přesně otázka, kterou si člověk před hospodou klade, a odpovídá to tónu appky. Min je taky stabilní vůči full-replace chování menu.

Serverová cenavšechny varianty potřebují PubPriceIndex — to je společný základ

Server ke každé hospodě v /v1/pubs/near aditivně přibalí pubDetails.price = { czk, volume_ml, observed_at, source } (jen neexpirované). Klient si z aktuálně načtené množiny postaví histogram a filtruje lokálně — přesně jako Airbnb, kde histogram ukazuje rozložení aktuálních výsledků.

  • Žádné čekání na server při posunu slideru — bary a počet hospod reagují okamžitě.
  • Funguje nad offline cache kompasu; výpadek syncu filtr nerozbije.
  • Starý klient nové pole ignoruje → nulové riziko kompatibility.
  • Slabina: histogram pokrývá jen načtený radius/viewport — což je pro „kam teď zajdu“ vlastně správně.

Přidat price_max do query /v1/pubs/near po vzoru vybaveností, včetně rozšíření fail-closed applied_filters acku.

  • Nutný bump ack logiky (starý backend by cenu tiše ignoroval) — přesně ta třída složitosti, kterou vybavenosti řeší, ale tady zbytečná: data ceny jsou v payloadu, klient si to ověří sám.
  • Každý pohyb slideru = nový request → latence + Mapy/proxy provoz.
  • Histogram by stejně potřeboval ceny v payloadu, takže B je nadmnožina A bez přidané hodnoty.

Nový GET /v1/pubs/price-histogram?lat&lng&radius vracející buckety spočítané serverem.

  • Jediná výhoda: přesný histogram i pro hospody, které klient nemá načtené (velká města, velké radiusy).
  • Nový endpoint = cache, rate-limity, verzování, provozní cena — proti zásadě „nepřidávej serverově drahou funkci bez důvodu“. Kdyby klientský histogram někdy nestačil, dá se C doplnit později, aniž by se cokoli z A zahazovalo.

Rizika

Řídká data na startu. Mimo města může mít cenu jen pár hospod → histogram s 3 bary vypadá chudě. Mitigace: sekce se schová pod ~5 známých cen v okolí a místo ní se ukáže výzva „Zmapuj cenu a pomoz ostatním“ (napojení na existující Mapér flow — cena už dnes XP nese přes menu contribution).
Vandalismus / překlep přepíše cenu. Drink-log merge je last-write; jeden útlý prst udělá z 45 Kč 450 Kč. Mitigace: rozsah 1–1000 už validuje API; do indexu navíc nepustit skoky > 3× oproti předchozí hodnotě z nižší priority zdroje (jen logovat). Víc neřešit — accept-and-flag vzor jako u drink anti-abuse.
Objemová srovnatelnost. „Nejlevnější ≥ 400 ml“ míchá 0,4 l a 0,5 l. Vědomě přijato — přepočet na litr by předstíral přesnost, kterou data nemají; UI vždy ukáže skutečný objem, když ≠ 0,5 l.

Provozně je změna levná: žádný nový endpoint, jeden indexovaný lookup navíc v už bounded /v1/pubs/near scanu, žádné volání Mapy.com navíc.
