Monorepo + branching pro Na pivo

návrh v2 17. 7. 2026 · po upřesnění záměru
0/0 kroků
Tvůj dev/main model je pro mobil správný. Pro backend nefunguje — a monorepo tuhle trhlinu odhalí.

Nechceš dev jako šuplík na nepořádek, chceš main jako zrcadlo toho, co mají lidi v telefonu. To je legitimní model a u mobilu dává smysl přesně z těch důvodů, co popisuješ: release je drahý, vzácný a schvalovaný, takže se vyplatí mít větev, kterou checkoutneš a hned z ní stavíš hotfix.

Jenže backend žádný „vydaný stav“ nemá — deployuje se průběžně, 104 commitů za 30 dní proti 8 mobilním releasům. Jedna větev main nemůže znamenat „to, co je ve store“ i „to, co běží na Hetzneru“ zároveň; jsou to různé commity v různý čas. To je přesně tvoje původní obava — a odpověď je, že backend se řídí tagy, ne větví.

Výsledek: dev + main pro mobil (tvůj model, beze změny) + api-* tagy pro backend. Pak monorepo sedne a backend deploy se main vůbec nedotkne.

Tvůj model, jak jsi ho popsal

Ať se bavíme o tomtéž — takhle jsem to pochopil:

Tenhle model funguje. Dřív jsem argumentoval proti dev jako proti šuplíku na rozdělanou práci — to není, co děláš. Ty používáš main jako pojmenovaný ukazatel na produkci, a to má reálnou ergonomickou hodnotu: git checkout main a víš, že stojíš na tom, co mají lidi v mobilu. Nemusíš nic dohledávat. To tag nenahradí stejně pohodlně.

Dvě místa, kde ti ten model zalže — ne fatálně, ale ať o nich víš:

1. Okno review. Mergneš dev → main, submitneš, Apple to schvaluje 1–3 dny. V tom okně main není „co lidi mají“, ale „co jsem poslal“. Když v tu chvíli přijde hotfix, checkoutneš main a stavíš nad verzí, kterou nikdo nemá.

2. Zamítnutý release. Apple to shodí. V main teď leží verze, co se nikdy nevydala, a invariant je pryč. To je přesně ten původní hřích, jen o patro výš.

Lék je levný a nemusíš kvůli němu na model sáhnout: tagni až to, co fakt vyjde (v1.5.0 ve chvíli, kdy je Ready for Sale, ne při submitu). Větev je pohodlí, tag je pravda. Když ty dva nesouhlasí, věř tagu.

Proč to samé nejde na backend

Tady je ta věc, kvůli které se tvoje branching otázka a tvoje monorepo otázka potkávají — a je to zároveň odpověď na to, na co ses ptal původně.

main jako „vydaná verze“ dává smysl jenom tam, kde je vydání událost. U backendu žádná událost není. Kdyby se backend deployoval z main, musel bys do main mergovat 104× za měsíc — a main by tím přestal být zrcadlem storu. A obráceně: kdyby backend čekal na mobilní release, dvakrát týdně bys nemohl nasadit opravu API.

Tohle je doslova tvoje původní otázka. Ptal ses: „když bude monorepo s jedním mainem, jak nasadím backend, aniž bych mergnul nehotový mobil?“ Odpověď: backend se z main nedeployuje vůbec. Deployuje se z dev, otagovaný jako api-*. main zůstane čistě mobilní věc — sáhne se na něj 2× do měsíce při releasu. Monorepo tenhle model nerozbije, protože se ty dvě komponenty o main nikdy nepoperou.

Ale backend tím pádem potřebuje vlastní ochranu

dev chrání mobil před nehotovou prací. Backend nechrání nic — v dev ti může ležet rozdělaný endpoint ve chvíli, kdy potřebuješ nasadit opravu. To je ta úplně stejná bolest, kvůli které jsi tenhle plán zadal, jen přestěhovaná. Proto backend tagy nejsou kosmetika: bez api-* tagu nemáš z čeho větvit backendový hotfix a jsi zpátky v pasti.

Výsledný model

Přesně jak jsi to popsal.

git checkout main && git merge dev        # vydávám, co je v devu
# bump verze: package.json + app.config.ts
eas build --profile production --platform all
eas submit --profile production --platform all
# ---- až je to Ready for Sale / published: ----
git tag v1.5.0 && git push origin main --tags

Tag až po vydání, ne po submitu — tím ošetříš zamítnutý release i okno review.

„Hele, rozbilo se tohle.“ Rozdělaná práce v dev tě nezajímá a nemusíš ji ani stashovat.

git worktree add ../napivo-hotfix -b fix/crash-na-mape main
cd ../napivo-hotfix
# … oprava, bump na 1.5.1 …
git commit -am "fix: prevent crash on empty map region"
git checkout main && git merge fix/crash-na-mape
eas build --profile production --platform all && eas submit --profile production --platform all
git tag v1.5.1                            # až je venku
git checkout dev && git merge main        # ← NEZAPOMENOUT

git worktree místo git checkout main: vedle vznikne druhý adresář, hlavní checkout s rozdělaným devem zůstane netknutý. Až budeš hotov: git worktree remove ../napivo-hotfix.

Ten poslední řádek je ta jediná daň za tvůj model. Když ho vynecháš, dev nemá fix, ty nad ním dál vyvíjíš a při příštím releasu ho můžeš omylem přepsat zpátky.

Průběžně z dev. Nemá to s main nic společného — proto tě monorepo nesváže.

# lokálně: otagovat, co chci nasadit
git tag api-2026.07.17.1 dev && git push origin dev --tags

# na serveru
cd /opt/na-pivo && git fetch origin --tags
git checkout --detach api-2026.07.17.1
cd backend
docker compose -p na-pivo run --rm web python manage.py migrate
docker compose -p na-pivo up -d --build

Tagovat i rutinní deploy vypadá jako buzerace — je to ale to jediné, díky čemu jde další panel udělat za 5 minut.

Tady main nepomůže — nasazený backend v něm není. Větví se z posledního api-* tagu.

git fetch origin --tags
git worktree add ../napivo-apifix -b fix/expired-tokens api-2026.07.17.1
cd ../napivo-apifix
# … oprava jen v backend/ …
git commit -am "fix: reject expired login tokens"
git tag api-2026.07.17.2 && git push origin fix/expired-tokens --tags
# deploy tagu (viz vedlejší panel), teprve pak:
git checkout dev && git merge fix/expired-tokens

Protože se větví z tagu, nezáleží na tom, co máš v dev rozdělaného. Kdybys neměl api-* tagy, musel bys deployovat dev — i s rozdělanou prací. Přesně to, čemu se vyhýbáš u mobilu.

Monorepo: ano, mobil zůstane v rootu

Když main = mobil a backend jede z tagů, ty dvě komponenty se v jednom repu o nic nepoperou. Monorepo je pak čistý zisk.

Expo aplikace zůstane v rootu, Django přibude do backend/. Nestěhovat mobil do mobile/ — přepsalo by to EAS root, nativní projekty ios/ a android/, metro config i credentials. Zisk nula, riziko velké.

Co tím získáš

  • Cross-stack featura = jedna větev, jeden commit. Podle historie je to u tebe standard, ne výjimka.
  • Agent vidí obě strany API kontraktu — méně „přidej to pole i do klienta“ ping-pongu.
  • Změna API a její klient v jednom diffu → kompatibilita jde reviewovat.
  • Jedny AGENTS.md, npm run dev bez ../.
  • Konec „commitnuto v obou repech, pushnuto v jednom“.

Co tě to stojí

  • Jednorázově ~1 h + překlopení serveru.
  • Backend historie se schová do backend/ — git log chce cestu.
  • Server tahá i mobilní historii (176 MB) — řeší --filter=blob:none.
  • Tagy v jednom jmenném prostoru → nutný prefix. Backend teď nemá žádné tagy, takže kolize nehrozí.
  • main bude obsahovat i backend kód, který je dávno nasazený z dev. Neškodné, ale mate.

Nejsilnější protiargument

Ta bolest, kvůli které se ptáš, zmizí už tím branchingem výš — a ten je zadarmo. Monorepo je pak už jen pohodlí a hodinu práce plus riziko na produkčním deployi je legitimní odložit. Proto: fáze 1 teď, monorepo až budeš mít nula nemergnutých větví (mobil má 3, backend 4).

Server: sparse checkout

Server si vytáhne na disk jen složku backend/ a stojí na api-* tagu. Mobilního kódu se nedotkne — ani ho nemá kde vzít.

# jednorázová konverze /opt/na-pivo
cd /opt/na-pivo
git remote set-url origin git@github-napivo:tomasmach/na-pivo.git
git fetch origin --tags --filter=blob:none   # netahá mobilní bloby
git sparse-checkout init --cone
git sparse-checkout set backend              # na disku je JEN backend/
git checkout --detach api-2026.07.17.1

Pozor — tichý zabiják

Docker Compose odvozuje jméno projektu z názvu adresáře. Až se docker compose začne pouštět z /opt/na-pivo/backend místo /opt/na-pivo, projekt se přejmenuje z na-pivo na backend a Compose vyrobí nové prázdné volumes — databáze zdánlivě zmizí. Proto všude explicitní -p na-pivo (přesné jméno ověř přes docker compose ls ještě před migrací), nebo rovnou name: na-pivo do docker-compose.yml.

A OTA

Tvůj OTA incident z parta-3 tenhle model řeší sám od sebe: OTA se publikuje z main, nikdy z dev. Kanály preview a production už v eas.json máš.

git checkout main
eas update --channel preview       # nejdřív si to sám ověř
eas update:republish --destination-channel production

update:republish promotuje identický bundle — nebuildí se znovu, takže do produkce nemůže proklouznout nic jiného, než co jsi otestoval v preview.

Kroky

Fáze 1 — branching (dneska, zadarmo)
  1. Otagovat, co běží na Hetznerubackend

    Backend nemá jediný tag → dnes deployuješ „co je zrovna v main“. Bez tagu nejde udělat backendový hotfix. Na serveru git -C /opt/na-pivo rev-parse HEAD, lokálně git tag api-2026.07.17.1 <sha>.

  2. Založit dev z aktuálního mainoba repy

    Pozor na pořadí: main teď obsahuje víc, než co je vydané (v1.4.0 je z 13. 7., od té doby do main přibyly věci). Takže: dev = dnešní main, a main se přetočí zpátky na v1.4.0, aby zase odpovídal storu.

    git checkout main && git pull
git checkout -b dev && git push -u origin dev   # dev = všechno, co mám
git checkout main && git reset --hard v1.4.0    # main = co je fakt ve storu
git push --force-with-lease origin main

    Force push na main. Nic se neztratí (všechno je v dev), ale je to nevratná operace na sdíleném refu — udělej ji vědomě. U backendu je to jinak: tam main = nasazený stav, takže reset na api-* tag, ne na v1.4.0. Nebo u backendu main zrušit úplně a nechat jen dev + tagy — backend „vydanou větev“ nepotřebuje.

  3. Přepnout default branch na devoba repy

    Na GitHubu Settings → Branches. Jinak budou PR i git clone mířit na main a dřív nebo později do něj něco spadne omylem. Případně na main zapnout branch protection.

  4. Zapsat model do AGENTS.mdoba repy

    Bez tohohle to za měsíc zapomeneme oba a agenti to nepřečtou nikde jinde. Musí tam být: co znamená dev/main, že tag vzniká až po vydání, že backend jede z api-*, že hotfix se dělá přes worktree, a že po mobilním hotfixu je nutný merge main → dev. AGENTS.md

  5. Uklidit nemergnuté větveoba repy

    Mobil: feat/other-drink-types, feat/venue-amenity-filters, fix/linear-backlog-sweep. Backend: 4 další. U každé dodělat a mergnout do dev, nebo smazat. Zároveň brána do fáze 2.

Fáze 2 — monorepo (~1 h, až je fáze 1 hotová)
  1. Vlít backend do backend/ se zachováním historieoba repy

    Subtree merge do dev (ne do main — ten je vydaná verze). Obě historie zůstanou, git log --follow backend/… funguje.

    git checkout dev
git remote add backend-src ../na-pivo-backend
git fetch --no-tags backend-src main:refs/remotes/backend-src/main
git merge -s ours --allow-unrelated-histories --no-commit backend-src/main
git read-tree --prefix=backend/ -u backend-src/main
git commit -m "chore: merge backend repository"
  2. Opravit dev-local.sh a zmínky v docsmobil

    Odkaz na sousední repo zmizí. scripts/dev-local.sh + 5 dalších souborů (README.md, AGENTS.md, docs/*.md).

    - BACKEND_DIR="$(cd "$(dirname "$0")/../../na-pivo-backend" && pwd)"+ BACKEND_DIR="$(cd "$(dirname "$0")/../backend" && pwd)"
  3. Přidat .easignoremobil

    Aby se Django netahalo do každého EAS buildu. Obsah = stávající .gitignore + řádek /backend. Bez tohohle se ti do buildu nahraje i backend/media/.

  4. Přidat deploy key mobilnímu repubackend

    Server má id_napivo / alias github-napivo jen pro backend repo. Bez toho git fetch na serveru spadne na permission denied. Udělat před překlopením serveru.

  5. Překlopit server na sparse checkoutbackend

    Nejdřív záloha DB. Pak přesun .env do backend/.env, sparse checkout, a hlídat -p na-pivo. Ověřit, že po přepnutí běží stará data — ne prázdná DB.

  6. Archivovat starý backend repozitářbackend

    Na GitHubu označit jako archived (read-only) s odkazem na nový domov. Lokální adresář nechat ležet týden, pak smazat.

Rizika

Force push na main (krok 2)

  • Přetočení main na v1.4.0 je nevratné. Před tím ověřit, že dev je pushnutý a obsahuje všechno. Alternativa: main nechat být a smířit se s tím, že první release ho srovná.

Zapomenutý merge main → dev

  • Jediná systémová daň tvého modelu. Po každém mobilním hotfixu. Nezachytí to nic než AGENTS.md a zvyk.

Compose volumes (krok 10)

  • Změna working directory může vyrobit nový Compose projekt a prázdné volumes. Vypadá to jako ztráta DB. Vždy -p na-pivo + záloha.

Deploy během přechodu

  • Mezi krokem 6 a 10 ukazuje server na starý repozitář. V tom okně nedělat backendový release, nebo krok 10 udělat hned po 6.
Co bych naopak nedělal
  • Nedeployoval backend z main. Rozbilo by to význam main a vrátilo tě to k původní pasti.
  • Nezaváděl release/* větve. Git Flow bez týmu a QA je čistá ceremonie.
  • Nestěhoval mobil do mobile/ při téhle migraci. Riziko na EAS/nativních projektech bez užitku.
  • Nezaváděl npm workspaces / Turborepo / Nx. Django a Expo nesdílí balíčky — není co spravovat.
  • Nespojoval migraci s CI. Když se něco rozbije, chceš vědět co.
  • Nezaváděl submoduly. Mají všechny nevýhody dvou repozitářů plus vlastní.
