Rychlejší start kompasu

Odstraněné dva nezávislé dlouhé chvosty: čekání na první přesný GPS fix a hromadný výpočet přechodu otevírací doby pro stovky nearby položek. Kompas může použít bezpečně čerstvý OS fix a detailní data se dál dopočítají mimo blokující cestu.

Výsledek profilu

Brno: 6,8 s → 349 ms při vypnutí bulk nextChange; SQL bylo jen ~0,1 s. Produkční p95 před opravou bylo 23,05 s.

Bezpečnost

Žádný nový provider, GPS historie ani produkční deploy. Detail vybrané hospody dál vrací přesný čas změny.

Kde může start čekat

První pracovní hypotéza: mobil čeká na první high-accuracy GPS fix ještě před pokusem o hydrataci snapshotu; při cache miss může následovat až desetisekundový síťový timeout. Produkční měření rozhodne, zda je backend samostatný bottleneck.

Stale-while-revalidate

Použít dostatečně čerstvou poslední známou polohu a pokrývající snapshot pro první render; současně spustit přesný watcher a síťový refresh. Přesný fix cíl opraví.

Server-only

Pomůže při pomalém API, ale neřeší dobu, kdy operační systém hledá první GPS fix.

Cache-only

Málo kódu, ale slabé chování po přesunu mezi městy a při chybějícím snapshotu.

Živý checklist

Očekávaný tvar změny

- čekat výhradně na BestForNavigation watcher
 načíst bezpečně čerstvou poslední známou polohu
 ihned rozběhnout watcher pro přesný fix
 použít lokální snapshot, když pokrývá pracovní polohu
 síťový refresh nechat mimo blokující cestu
Bezpečnostní hranice

Last-known fix bude mít limit stáří a přesnosti. Aplikace nebude ukládat trasu ani přidávat souřadnice do telemetrie. Při přesunu nebo nekvalitním fixu zůstane stávající loading/empty flow.

Rizika

Stará poloha

Po cestě mezi městy nesmí starý fix krátce ukázat hospodu stovky kilometrů daleko. Řeší limit stáří/přesnosti a následná coverage kontrola.

DB plán

Výrazové řazení v bounding boxu může pod produkčním objemem zhoršit tail latency. Index přidáme jen s důkazem z EXPLAIN/latencí.
