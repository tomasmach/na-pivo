Datový invariant

Uživatel po merge nesmí poznat ztrátu.

Počet jeho drink logů, návštěv a aktivit zůstane stejný. Žádný uživatelský řádek se nemaže ani nepřepisuje; při čtení aktuálního menu a vybavení se nad zachovanými vstupy použije deterministické pravidlo. Audit eviduje dotčené tabulky a přesně deaktivované katalogové řádky. Starý mobilní klient i opožděná offline fronta se přes alias přesměrují na kanonickou hospodu.

API filtr

Odstraní vizuální symptom, ale menu, hodnocení a statistiky zůstanou na dvou identitách. Není to splnění zadání.

Přepis klíčů

Bez trvalého aliasu se problém vrátí po prvním zápisu ze staré aplikace nebo offline fronty. Navíc neumí bezpečně řešit unikátní konflikty.

Alias + doménový merge

Kanonická identita je stabilní; zdrojové identity jsou auditovatelné aliasy. Každá datová oblast má explicitní merge pravidlo a příkaz nejdřív generuje dry-run.

Pravidla pro konflikty

Drinky, návštěvy, aktivity

Všechny řádky zůstanou. Změní se jen jejich hospodská identita; počet musí být před a po shodný.

Komunitní menu

Union podle kanonického pivního produktu, objemu a ceny. Uživatelský aktuální stav má přednost před externím fallbackem.

Hodnocení

Pro stejného uživatele vyhraje novější client_updated_at. Oba vstupy se zapíšou do merge auditu.

Vybavení

LWW po uživateli a amenity. Veřejné agregáty se zahodí jako odvozená data a znovu přepočítají.

XP a achievementy

Ledger se deduplikuje, ale již udělené XP ani lifetime countery se nesnižují a znovu neudělují.

Katalog

Zdrojové řádky se nemažou. Deaktivují se a zůstanou dohledatelné přes alias a audit.

Rizika a pojistky

Největší riziko: nepravdivé automatické spárování.

Google Place ID není samo o sobě autoritativní; současný offline matching obsahuje falešné shody v areálech. Automaticky lze vzít jen úzkou silnou třídu, zbytek zůstane v review queue.

Kolize unikátních constraintů

Rating, amenity vote, menu indexy a XP ledgery mohou mít záznam na obou klíčích. Merge musí konflikt vyřešit před změnou klíče a celý běžet v jedné transakci.

Staré mobilní verze a offline queue

Alias resolver musí být na serveru trvalý. Vstup se starými souřadnicemi se kanonizuje; jinak by se duplicita po opravě znovu narodila.

Rollback

Před každým produkčním batchem vznikne DB backup a auditní snapshot. První batch obsahuje jen dvě ručně potvrzené dvojice.

Rozhodnutí

Uživatel dal implementační svobodu; doporučené volby jsou předvyplněné a představují pracovní rozhodnutí. Formulář lze použít, pokud je chce později změnit.
