Lokální adresář hospod — instantní mapa, minimum API dotazů

11. 7. 2026 · návrh · backend na-pivo-backend, drobnosti v na-pivo

TL;DR: Ano, jde to. Po doběhnutí scrape budeme mít vlastní adresář ~28k českých podniků (jméno, GPS, město, otevíračka, rating, klasifikace). Naimportujeme ho do produkčního Postgresu a /v1/pubs/near začne odpovídat přímo z DB — mapa se otevře instantně, bez čekání na Mapy.cz. Mapy zůstanou jen jako fallback pro Slovensko a nepokryté oblasti; firmy.cz proxy jen na pomalý refresh. Úplně odejít od obou zdrojů nejde (SK data, čerstvost, nové podniky), ale API dotazy klesnou odhadem o 80–95 %.

Cíle / Ne-cíle

  • Cíl: mapa i kompas ukazují podniky z vlastní DB — p50 odezva v jednotkách ms místo stovek ms.
  • Cíl: Mapy.cz kredity a firmy.cz proxy GB srazit na zlomek (fallback + refresh).
  • Cíl: žádná změna mobilního API — response shape /v1/pubs/near zůstává beze změny (vydané verze!).
  • Ne-cíl: úplné odpojení Mapy.cz — SK pokrytí, geocoding/suggest a čerstvost je pořád potřebují.
  • Ne-cíl: real-time čerstvost dat; pracujeme s TTL a lazy refreshem.

Architektura

Klíčový vhled: wire formát /v1/pubs/near je maličký — {name, label, position{lat,lon}, regionalStructure[{name,type}]} — a náš katalog (name, lat, lng, city) ho umí naplnit 1:1. Mobilní appka nepozná rozdíl.

Kroky

  1. Doběhnutí scrape + quality pass — spočítat finální čísla, vyhodit šum (generická jména bez matche, venue_kind=not_pub dle produktového rozhodnutí), dedupe geohash8+jméno.
    detailŠum typu „Přístřešek“/„Jez“ se do adresáře nesmí dostat — mapa by ukazovala nesmysly. Heuristika: importovat jen záznamy, které (a) mají firmy match, NEBO (b) mají hospodské jméno (hospoda/hostinec/pivnice/bar/restaurace… v názvu) a nejsou v generickém blocklistu. Hraniční případy projít ručně nad výslednými počty.
  2. Port multi-candidate fixu do main — produkční lazy refresh_hours má stejný first-link bug; malý cherry-pick/port commitu fb4c6ba (jen firmy.py + testy).
  3. Model PubDirectory + migrace (main) — name, lat, lng, geohash6 (indexed), city, venue_kind, source, refreshed_at; unikát na (geohash8, normalizované jméno).
    proč nový model, a ne PubSearchCachePubSearchCache cachuje výsledky dotazů (cell+radius → JSON blob), ne entity. Adresář je entita per podnik — umožní bbox dotazy, ruční korekce, budoucí obohacování (amenities, fotky) a periodický refresh per záznam. PubSearchCache zůstane pro Mapy fallback beze změny.
  4. Import command import_pub_directory — načte katalog JSON + bulk.sqlite3, naplní PubDirectory a upsertne PubHours řádky do produkce (stejný model + cache_key, přesun je přímočarý). Idempotentní, s --dry-run.
  5. DB-first čtecí cesta v PubsNearView — bbox dotaz nad PubDirectory (lat/lng btree + haversine dořez, na ~30k řádcích triviální), serializace do trimmed-item shape. Uvnitř CZ polygonu je DB autoritativní (žádný Mapy call); mimo něj beze změny stávající cesta. Za feature flag PUBS_NEAR_LOCAL_FIRST.
    golden test parityTest porovná serializovaný DB item s trimmed Mapy itemem pro stejný podnik — pojistka proti rozbití vydaných mobilních verzí (itemToPub v appce).
  6. Hodiny instantně — importem PubHours se POST /v1/pub-hours stane čistým cache hitem; TTL pro bulk-importované řádky zvednout (30 → 90 dní), ať proxy GB klesnou.
  7. Freshness smyčka — kvartální re-run bulk scrape z domácí IP (resume-safe), existující lazy refresh, user reporty (report-pub-removal) a user-added pubs beze změny.
  8. Rollout — deploy migrace + import na Hetzner, flag zapnout, sledovat telemetrii: fallback rate, Mapy kredity, p50 latence. Rollback = flag vypnout.

Rizika a otevřené otázky

  • Licence: katalog pochází z Mapy.cz suggest (Extended tarif má podmínky — ověřit, co říká o ukládání/redistribuci POI) a firmy.cz robots.txt crawling zakazuje. Pro dlouhodobý provoz zvážit Seznam B2B licenci (viz poznámka v firmy.py). Rozhodnutí je na tobě — technicky jedeme dál, ale ať je to vědomé riziko.
  • Čerstvost: hospody zavírají; adresář bez refreshe zestárne. Mitigace: kvartální re-scrape + user reporty. Zavřený podnik na mapě je horší UX než pomalejší mapa — proto TTL a refresh nesmí uschnout.
  • SQLite → PG: import psát a testovat proti lokálnímu Postgresu, ne sqlite (sqlite už jednou schoval migrační bug).
  • Rozhodnuto (11. 7.): SK katalog sweepneme přes Mapy hned po CZ běhu — scripts/run_bulk_sk.sh (nový flag --catalogue-only, žádný firmy fill). Mapa bude instantní i na Slovensku (podniky + GPS + město).

Apify pro SK — nejlepší cesta k hodinám

Apify Google Maps Scraper obchází mrtvé SK katalogy úplně — tahá z Google Maps, kde jsou SK podniky i s otváracími hodinami. Jeden managed actor, nic se nestaví. Vrací jméno, GPS, adresu, otváracie hodiny, rating, kategórie naráz.

ActorCenaPozn.
compass/crawler-google-places~$4 / 1000nejpopulárnější, nejspolehlivější
microworlds/crawler-google-places~$1 / 1000levnější alternativa

Odhad SK: ~10–15k podniků → jednorázově cca $10–60. Actor umí katalog i hodiny zároveň — pro SK tedy vůbec nemusíme dělat Mapy sweep, jeden Apify běh dodá všechno. Výstup (JSON) naimportujeme do PubDirectory + PubHours stejným importem jako CZ.

Caveat: Google Maps ToS scraping/ukládání dat nepovoluje — stejná šedá zóna jako firmy.cz (konzistentní s dosavadním postojem, ale vědomé riziko). A z Google Maps leze podobný šum v názvech → projede stávající venue_kind klasifikace.

Doporučení pro SK:

  1. Cesta A (doporučeno): jeden Apify Google Maps běh přes SK bbox/města → katalog + hodiny + rating naráz, ~$10–60 jednorázově. Import stejný jako CZ.
  2. Cesta B (zdarma, hned): Mapy sweep katalogu bez hodin (run_bulk_sk.sh, hotové) + hodiny nechat na komunitu přes „Zmapuj hospodu“ (Mapér XP).
  3. Dá se kombinovat: spustit B teď kvůli rychlé mapě, A přidat, až budeš chtít i hodiny.

Pozn.: stávající Apify hand-off v bulk_fill_hours (delectable_incubator/firmy-cz-scraper) je jiný actor — jen firmy.cz / CZ. Pro SK jde o samostatný Google-Maps actor a samostatný import, ne o --remaining-out cestu.
